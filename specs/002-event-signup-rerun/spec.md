## Clarifications

### Session 2026-09-27

使用者一次答完 42 題(編號沿用使用者的 3–44,即標記出現順序)。

- Q3: 開賣、截止時間恰好相等那一刻可否保留? → A: 開賣時間 ≤ 現在 < 截止時間才能保留;恰等於開賣可以,恰等於截止不行。
- Q4: 過了截止時間,狀態會自動變已截止嗎? → A: 不會。狀態與時間是兩個真相來源,各自擋:狀態不是開賣中 → 409 `not_on_sale`;時間不在區間內也回 409 `not_on_sale`。
- Q5: 已過到期但尚未翻成過期的保留,座位怎麼顯示?清理多久一次? → A: 依到期時間判斷,保留中且到期時間 > 現在才算保留中;定期清理每 5 分鐘一次。
- Q6: 放棄非保留中的保留? → A: 409 `terminal_state`;非本人 → 404。
- Q7: 重複確認的細節? → A: 保留已確認時一律回那張訂單 200,不看這次帶的優惠碼、也不看到期時間;訂單已取消(保留變已取消)後再確認 → 409 `terminal_state`。
- Q8: 保留請求本身不合法? → A: 座位清單為空、超過 10 席、同請求內重複、編號不在 A–J × 1–10 → 400 `invalid_input`;票種不屬於此活動 → 404 `not_found`。
- Q9: 無效碼與平手規則在同額時矛盾? → A: 作者 2026-09-27 定:無效碼只有「會讓應付**嚴格**更低」或「沒有任何別的折扣」時才 409;同額 → 忽略碼,訂單照擇優成立。平手順序只用在有效折扣之間。原文兩句矛盾,列入 `spec-writeback.md`。
- Q10: 不存在的碼沒有面額怎麼判斷? → A: 有別的折扣 → 忽略;沒有別的折扣 → 409 `promo_rejected`。
- Q11: 0 元票種輸入優惠碼? → A: 有效碼 → 三候選都是 0,不算「更低」,碼不套用、不記、不算用掉(碼狀態「不划算」);無效碼 → 沒有別的折扣 → 409。**【待作者確認】**:repo 現況對「存在但無效」的碼在小計 0 時是忽略(201)。
- Q12: 碼有效期的相等邊界、大小寫? → A: 現在 < 有效期限才有效,相等即失效;碼不分大小寫。
- Q13: 重複截止、對已截止或已結束活動截止? → A: 409 `terminal_state`。
- Q14: 改時間會影響狀態嗎? → A: 不會;狀態機沒有 已截止 → 開賣中。
- Q15: 活動截止或結束後可否取消訂單? → A: 可以;取消只看訂單是否已確認。
- Q16: 撤銷後既有存取憑證? → A: 撤銷只作用在續期憑證;存取憑證撤銷後仍可用到 15 分鐘到期。
- Q17: email 大小寫與格式? → A: 一律轉小寫存,唯一不分大小寫;只檢查含 @、長度 3–254。
- Q18: 暱稱與密碼規則? → A: 暱稱必填 1–50 字,不唯一;密碼 ≥ 8,無上限、無其他規則。
- Q19: 輪替後的 30 天怎麼算? → A: 從輪替當下重新起算。
- Q20: 登入失敗計數對象? → A: 帳號;不存在的 email 不計數,一樣回 401 `unauthorized`。
- Q21: 鎖定階梯怎麼走? → A: 連錯 5 次鎖 5 分鐘;鎖定到期後計數不歸零,再錯 1 次就進下一階(10 → 20 → 40 → 60 分鐘,上限 60);成功登入計數歸零、階梯退回起點;鎖定中的嘗試不驗密碼、不計數。
- Q22: 建活動欄位驗證? → A: 開賣 < 截止;可以是過去時間;團體門檻 ≥ 2;團體折扣 0–100%;名稱 1–100 字。
- Q23: 座位編號? → A: 列 A–J、欄 1–10,如 A1、J10。
- Q24: 什麼時候轉已結束? → A: 目前沒有自動轉已結束的排程,只能由管理者直接改資料。**【待作者確認】**是否要在截止時間之後由排程轉。
- Q25: 列表篩選? → A: 篩選值 = 草稿 / 開賣中 / 已截止 / 已結束,其他值 → 400;「開賣中」只看狀態、不排除已過截止時間的;預設列表含已截止與已結束,不含別人的草稿。
- Q26: 座位狀態分幾種? → A: 四種:空(free)/ 他人保留中(held)/ 已售(sold)/ 自己的(mine,自己保留中的)。**【待作者確認】**:repo 現況把自己**已確認**的座位也顯示為 mine。
- Q27: 「改名額」改什麼? → A: 改各票種名額,一次可改多個;全有全無:任一項低於已售 → 409 `capacity_below_sold`,總和 > 100 → 409 `capacity_exceeded`,整次修改不寫入。
- Q28: 改活動可改哪些欄位? → A: 名稱、開賣時間、截止時間、保留時長、團體門檻、團體折扣,以及票種名額。
- Q29: 票種欄位範圍? → A: 早鳥截止時間可省略(= 沒有早鳥);早鳥折扣預設 0、範圍 0–100;價格為整數分且 ≥ 0;名額 0–100。
- Q30: 何時可新增票種? → A: 任何狀態都可,只受名額總和 ≤ 100 限制。
- Q31: 放棄與取消後的紀錄? → A: 一樣留著,只改狀態。
- Q32: 試算對非保留中的保留? → A: 已過期 → 409 `hold_expired`;已放棄或已確認 → 409 `terminal_state`;非本人 → 404。
- Q33: 試算的碼狀態值、時間基準? → A: 無碼(none)/ 已套用(applied)/ 不划算(not_better)/ 無效(invalid);以試算當下時間判斷碼的有效期。
- Q34: 我的票券列哪些? → A: 本人所有訂單(含已取消與已報到),不含保留;依確認時間新到舊。
- Q35: 已取消訂單顯示 QR 嗎? → A: 明細仍回 QR 內容;web 只對已確認訂單顯示取消按鈕。
- Q36: 主辦操作在 web 哪裡? → A: 只透過 API;web 五個畫面不放主辦功能(非目標 11:不做管理後台)。
- Q37: web 要有放棄、取消入口嗎? → A: 要:保留倒數畫面有「放棄」,我的票券對已確認訂單有「取消訂單」。
- Q38: iOS 座位圖在哪? → A: 列表只列活動;座位圖在點進活動後的明細畫面。
- Q39: 金額顯示格式? → A: NT$ 加千分位,整元不顯示小數,有分才顯示兩位(12345 分 → NT$123.45;100000 分 → NT$1,000);轉換全程整數。
- Q40: 時間顯示時區? → A: web 用瀏覽器時區、繁中(zh-TW)格式顯示。
- Q41: 完整錯誤代碼? → A: `invalid_input` 400、`unauthorized` 401、`refresh_replayed` 401、`forbidden` 403、`not_found` 404;409:`email_taken`、`not_on_sale`、`seat_taken`、`hold_exists`、`sold_out`、`hold_expired`、`terminal_state`、`capacity_below_sold`、`capacity_exceeded`、`promo_rejected`。對應見 FR-090。
- Q42: 403 還是 404? → A: 「僅本人」的資源(保留、訂單)對別人一律 404,不透露存在;主辦限定的寫入(活動、票種)對非主辦 403;別人的草稿活動 → 404。
- Q43: 登入失敗與鎖定狀態記在哪? → A: 作者已決定記在成員資料上(連續失敗次數、鎖定到期時間)。
- Q44: 讀取次數要算到什麼程度? → A: 量「我的票券」一次載入的資料讀取列數,記下數字即可,沒有目標值。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 成員選位、保留並確認報名 (Priority: P1)

成員在活動開放報名期間,從 10×10 的座位中選一個或多個座位、指定一個票種,取得有時效的保留;
在保留到期前確認,產生訂單。保留逾時自動釋放,座位可被別人搶到。

**Why this priority**: 原文「做完定義」⭐ 列:「併發測試通過(不超賣、不重座),且金額路徑零浮點,
且保留逾時的三方競態有明確且被測試釘住的行為」—— 原文稱之為「整個專案的重心」。

**Independent Test**: 準備一個開賣中、已設票種的活動,單獨驗證「保留 → 確認 → 訂單」、
併發搶同一座位、併發搶同一票種名額、以及到期那一刻的三方競態。

**Acceptance Scenarios**:

1. **Given** 活動狀態為開賣中、開賣時間 ≤ 現在 < 截止時間、所選座位空著、票種剩餘名額足夠,
   **When** 成員指定一個票種與 1–10 個座位送出保留,
   **Then** 保留成立,到期時間 = 建立時間 + 該活動的保留時長;所選座位別人搶不到;票種名額在建立保留時就扣除。
2. **Given** 一次保留多個座位,其中一席已被別人占住,
   **When** 送出,
   **Then** 整批失敗,**沒有任何一個座位被鎖住**,409 `seat_taken`。
3. **Given** 票種剩餘名額少於本次要保留的座位數,**When** 送出,**Then** 整批失敗,409 `sold_out`,沒有座位被鎖,名額不變。
4. **Given** 座位衝突與名額不足同時發生,**When** 送出,**Then** 409 `seat_taken`(先檢查座位)。
5. **Given** 活動狀態不是開賣中(例如已截止),**When** 送出保留,**Then** 409 `not_on_sale`。
6. **Given** 活動狀態仍是開賣中,但現在時間 ≥ 截止時間(含恰好相等),**When** 送出保留,**Then** 409 `not_on_sale`。
7. **Given** 現在時間 < 開賣時間,**When** 送出保留,**Then** 409 `not_on_sale`;現在時間恰等於開賣時間則可以保留。
8. **Given** 成員在同一活動已有一個有效保留,**When** 再送出保留,**Then** 409 `hold_exists`。
9. **Given** 座位清單為空、超過 10 席、同一請求內座位重複、或座位編號不在 A–J × 1–10,**When** 送出,**Then** 400 `invalid_input`。
10. **Given** 指定的票種不屬於此活動,**When** 送出,**Then** 404 `not_found`。
11. **Given** 本人的保留尚未到期,**When** 本人確認,**Then** 建立訂單(201),金額依確認當下的票價與折扣規則計算並存成快照。
12. **Given** 保留已確認過,**When** 同一保留再確認一次(不論這次帶什麼優惠碼、不論是否已過到期時間),**Then** 回**同一張訂單**(200),不建第二張。
13. **Given** 保留確認後訂單已被取消,**When** 再確認,**Then** 409 `terminal_state`。
14. **Given** 保留已到期,**When** 確認,**Then** 409 `hold_expired`,且該保留的座位已釋放、可被別人保留。
15. **Given** 現在時間恰好等於到期時間,且「原持有人確認」「別人搶同一座位」「系統清理過期保留」同時發生,
    **When** 三者競爭,
    **Then** **原持有人的確認一律失敗**:到期那一刻就算過期。
16. **Given** 主辦已提前截止活動,**When** 截止前建立、尚未到期的保留被確認,**Then** 201 —— 確認只看保留自己的到期時間,不看活動狀態或截止時間。
17. **Given** 本人有一個保留中的保留,**When** 本人主動放棄,**Then** 保留變已取消,座位釋放,票種名額還回。
18. **Given** 保留已不是保留中(已過期、已確認、已放棄),**When** 本人放棄,**Then** 409 `terminal_state`。
19. **Given** 保留不是自己的,**When** 確認、試算或放棄,**Then** 404 `not_found`(不透露存在)。
20. **Given** 保留中,**When** 想改座位或票種,**Then** 沒有這個操作;須放棄後重新保留。
21. **Given** 成員已買過同一活動,**When** 再保留同一活動,**Then** 允許(限制的只是同時一個保留中)。
22. **Given** staff 是某活動的主辦,**When** 他保留自己主辦的活動,**Then** 允許(staff 也是成員)。

### User Story 2 - 帳號:註冊、登入、續期、登出 (Priority: P1)

使用者以 email + 密碼 + 暱稱註冊成為成員(單一組織),登入取得存取憑證與續期憑證;
續期時輪替,偵測到舊續期憑證被重放時強制重新登入;登入連續失敗會被鎖定。

**Why this priority**: 除註冊與登入外,原文所有操作都要求成員身分。原文把「自製登入憑證」列為題目本身(非目標 12)。

**Independent Test**: 不需要任何活動資料,單獨以註冊 → 登入 → 續期 → 重放 → 登出 → 連續輸錯驗證。

**Acceptance Scenarios**:

1. **Given** email 未被使用(不分大小寫)、含 @ 且長 3–254、密碼 ≥ 8 字元、暱稱 1–50 字,**When** 註冊,
   **Then** 建立角色為一般成員的帳號,email 以小寫保存;不做 email 驗證。
2. **Given** email 已被使用(含只差大小寫),**When** 註冊,**Then** 409 `email_taken`。
3. **Given** email、密碼或暱稱不合規則,**When** 註冊,**Then** 400 `invalid_input`。
4. **Given** 帳密正確且未被鎖定,**When** 登入,**Then** 取得有效 15 分鐘的存取憑證與有效 30 天的續期憑證。
5. **Given** 有效的續期憑證,**When** 續期,**Then** 發出新的續期憑證(30 天自此刻起算),舊的立刻失效。
6. **Given** 一張已被輪替掉的舊續期憑證,**When** 有人拿它續期(重放),**Then** 401 `refresh_replayed`,撤銷該成員**全部**續期憑證,該成員必須重新登入。
7. **Given** 已登入,**When** 登出,**Then** 撤銷當前的續期憑證;已發出的存取憑證仍可用到 15 分鐘到期。
8. **Given** 同一帳號連續輸錯密碼 5 次,**When** 第 5 次失敗,**Then** 鎖定 5 分鐘。
9. **Given** 鎖定已到期、計數未歸零,**When** 再錯 1 次,**Then** 進下一階;鎖定時間依序 10 → 20 → 40 → 60 分鐘,上限 60 分鐘。
10. **Given** 帳號鎖定中,**When** 登入(即使密碼正確),**Then** 一律 401 `unauthorized`,不驗密碼、不透露被鎖、不累計。
11. **Given** 曾有登入失敗,**When** 成功登入,**Then** 失敗計數歸零、階梯退回 5 分鐘起點。
12. **Given** 不存在的 email,**When** 登入,**Then** 401 `unauthorized`,不計數。

### User Story 3 - 主辦建立與管理活動、票種 (Priority: P2)

staff 建立活動(建立者即該活動的主辦),為活動設定票種;主辦可以改名額與時間、改票價、手動提前截止。
其他人(包括其他 staff)對別人的活動一律被拒。主辦操作只透過 API,web 沒有主辦畫面。

**Why this priority**: 原文「做完定義」:「只有主辦能改名額與時間;測試證明越權被拒」。沒有活動與票種,US1 無從進行。

**Independent Test**: 以一位 staff、另一位 staff、一位一般成員,驗證建立、改動與越權被拒。

**Acceptance Scenarios**:

1. **Given** staff 已登入,**When** 建立活動並給名稱(1–100 字)、開賣時間、截止時間(開賣 < 截止,可以是過去)、
   團體門檻(≥ 2)、團體折扣百分比(0–100)、保留時長(5–30 分鐘),
   **Then** 活動建立後**直接是開賣中**;座位固定 10×10 = 100 席;建立者成為主辦。
   未給團體門檻、團體折扣百分比、保留時長時,分別為 4、10、10 分鐘。
2. **Given** 欄位不合上述範圍(例如保留時長不在 5–30、開賣 ≥ 截止),**When** 建立活動,**Then** 400 `invalid_input`。
3. **Given** 一般成員(非 staff),**When** 建立活動,**Then** 403 `forbidden`。
4. **Given** 主辦,**When** 新增票種並給名稱、價格(整數分 ≥ 0)、名額(0–100)、早鳥截止時間(可省略 = 沒有早鳥)、
   早鳥折扣百分比(預設 0,0–100),**Then** 票種建立(不論活動狀態);
   **若**該活動所有票種名額總和會超過 100,**Then** 409 `capacity_exceeded`。
5. **Given** 主辦改票價,**When** 重讀改價前已確認的訂單,**Then** 金額不變;尚未確認的保留在確認時以新價計。
6. **Given** 主辦一次改多個票種的名額,其中任一項小於已售出(已售 = 名額 − 剩餘,保留中的座位算已售),
   **When** 送出,**Then** 409 `capacity_below_sold`,**整次修改都不寫入**。
7. **Given** 主辦改票種名額後總和 > 100,**When** 送出,**Then** 409 `capacity_exceeded`,整次修改都不寫入。
8. **Given** 主辦改開賣或截止時間,**When** 送出,**Then** 活動狀態不變(已截止的活動不會因此回到開賣中)。
9. **Given** 主辦提前截止開賣中的活動,**When** 之後有人送出新保留,**Then** 409 `not_on_sale`;截止前已存在的有效保留不受影響(見 US1 情境 16)。
10. **Given** 活動已截止或已結束(或重複截止),**When** 主辦再截止,**Then** 409 `terminal_state`。
11. **Given** 主辦改保留時長,**When** 之後有人保留,**Then** 新保留用新時長;已存在的保留不受影響。
12. **Given** 非主辦(一般成員或其他 staff),**When** 改活動、提前截止、新增票種或改票價,**Then** 403 `forbidden`。

### User Story 4 - 折扣擇優與試算 (Priority: P2)

確認時系統在三種折扣(早鳥、團體、優惠碼)中只套一種 —— 讓應付金額最低的那一種;
成員在確認前可以試算,看到原價、會套用哪種折扣、應付金額與優惠碼狀態,試算不建訂單、不用掉優惠碼。

**Why this priority**: 金額是 ⭐ 列三個條件之一;原文 2026-09-27 改定為「不疊加,擇優」,並給了驗算用的例子。

**Independent Test**: 以固定的小計、早鳥、團體與優惠碼組合,驗證試算與確認的應付金額、訂單上記錄的折扣欄位。

**Acceptance Scenarios**:

1. **Given** 小計 100000 分、早鳥 10%、團體 10%(已達門檻)、有效優惠碼 10000 分,
   **When** 確認,**Then** 三個候選都是 90000 → 平手,選優惠碼 → 應付 90000 分(NT$900)。
2. **Given** 只有一種折扣符合,**When** 確認,**Then** 套該種。
3. **Given** 三種都不符合,**When** 確認,**Then** 應付 = 小計。
4. **Given** 優惠碼面額大於小計且被選中,**When** 確認,**Then** 應付 0,訂單記的折抵金額 = 小計(實際折抵,不是碼面額)。
5. **Given** 帶了有效優惠碼但沒被選中,**When** 確認,**Then** 訂單不記優惠碼、折抵為 0,**碼不算用掉**,同一活動之後還能用。
6. **Given** 優惠碼無效(存在但過期、不屬於此活動、已用過),且假設它有效時會讓應付**嚴格**低於其他最佳折扣,
   **When** 確認,**Then** 409 `promo_rejected`。
7. **Given** 優惠碼無效,且別的折扣本來就比它好**或一樣好**,**When** 確認,**Then** 忽略這個碼,訂單照擇優成立。
8. **Given** 優惠碼不存在,**When** 確認,**Then** 有別的折扣 → 忽略碼、訂單成立;沒有別的折扣 → 409 `promo_rejected`。
9. **Given** 成員在某活動用過某碼的訂單後來被取消,**When** 他在同一活動再用這個碼,**Then** 可以用(只算有效訂單)。
10. **Given** 保留建立時早鳥仍有效、確認時早鳥已過,**When** 確認,**Then** 早鳥仍符合(早鳥看建立保留的時間)。
11. **Given** 優惠碼,**When** 確認,**Then** 碼在「現在 < 有效期限」時有效,恰等於有效期限即失效;碼不分大小寫。
12. **Given** 0 元票種,**When** 保留並以有效碼確認,**Then** 允許;碼不套用、不記、不算用掉(碼狀態「不划算」)。
13. **Given** 0 元票種,**When** 以無效碼確認,**Then** 409 `promo_rejected`(沒有別的折扣)。
    **【待作者確認】**:repo 現況只有「不存在的碼」會 409;「存在但無效」的碼在小計為 0 時被忽略、訂單成立(201)。
14. **Given** 本人保留中的保留,**When** 試算(可帶優惠碼),**Then** 回原價、套用哪種折扣、應付金額、碼狀態(無碼 / 已套用 / 不划算 / 無效);
    不建訂單、不用掉碼;碼的有效期以試算當下時間判斷。
15. **Given** 保留已過期,**When** 試算,**Then** 409 `hold_expired`;保留已放棄或已確認 → 409 `terminal_state`。

### User Story 5 - 我的票券、明細與取消 (Priority: P3)

成員查看自己的票券列表與單筆明細(含金額快照與票券 QR);可以取消已確認的訂單,座位釋放可再售。
主辦可以查看自己活動的訂單明細。

**Why this priority**: 原文「做完定義」第三列:「web 與 iOS 對同一個 GET 顯示同一份資料,且讀取次數有算過」。

**Independent Test**: 以一張已確認的訂單驗證列表、明細、QR 內容、取消後座位可再被保留。

**Acceptance Scenarios**:

2. **Given** 訂單本人或該活動主辦,**When** 查看明細,**Then** 看到金額快照與票券 QR;QR 內容是訂單 id + 簽章的短字串,不含任何個資。
   已取消的訂單明細仍含 QR 內容。

6. **Given** 已取消的訂單,**When** 嘗試轉成任何狀態,**Then** 409 `terminal_state`。
7. **Given** 訂單不是自己的,**When** 取消,**Then** 404 `not_found`。

### Edge Cases

- 開賣時間、截止時間的相等邊界:開賣時間 ≤ 現在 < 截止時間才能保留(US1 情境 6、7)。
- 活動狀態(開賣中/已截止)與開賣、截止時間是**兩個真相來源**,兩者都要檢查,且每個邊界的測試分開寫(原文 ⚠️)。
  過了截止時間,狀態**不會**自動變已截止;兩種情況都回 409 `not_on_sale`。
- 保留已過到期時間、但尚未被翻成過期時:座位狀態依到期時間判斷,顯示為空;系統每 5 分鐘清理一次過期保留,
  搶位時也會當場釋放(FR-047)。
- 放棄非保留中的保留 → 409 `terminal_state`(US1 情境 18)。
- 同一保留重複確認:已確認 → 回同一張訂單 200(不看優惠碼、不看到期);訂單已取消後再確認 → 409 `terminal_state`。
- 保留請求本身不合法 → 400 `invalid_input`;票種不屬於此活動 → 404 `not_found`。
- 無效優惠碼與平手規則:同額時忽略碼(作者 2026-09-27 定;原文兩句在同額時矛盾,見 `spec-writeback.md`)。
- 不存在的優惠碼:有別的折扣 → 忽略;沒有 → 409 `promo_rejected`。
- 小計為 0(0 元票種):見 US4 情境 12、13(含【待作者確認】)。
- 優惠碼有效期恰等於現在 → 已失效;碼不分大小寫。
- 提前截止已截止或已結束的活動 → 409 `terminal_state`。
- 改截止時間到未來不會讓已截止的活動重新開賣;沒有 已截止 → 開賣中。
- 活動已截止或已結束後,已確認的訂單仍可取消。
- 登出或重放撤銷的是續期憑證;已發出的存取憑證仍可用到 15 分鐘到期。

## Requirements *(mandatory)*

### Functional Requirements

**範圍**

- **FR-001**: 系統 MUST 只提供原文列出的 18 項對外操作(帳號 4、活動 5、票種 2、保留與確認 4、訂單 3),不得新增。
- **FR-002**: 系統 MUST 只服務單一組織(非目標 5)。
- **FR-003**: 系統 MUST NOT 收款;只記帳(非目標 3)。退款金額不計算。

**帳號與身分**

- **FR-010**: 使用者 MUST 能以 email(唯一)+ 密碼(≥ 8 字元)+ 暱稱註冊;不做 email 驗證。
  email 一律轉小寫保存,唯一性不分大小寫,只檢查含 @、長度 3–254;暱稱必填 1–50 字、不需唯一;密碼 ≥ 8 字元,沒有上限與其他規則。
- **FR-011**: 登入 MUST 發出有效 15 分鐘的存取憑證與有效 30 天的續期憑證。
- **FR-012**: 續期 MUST 輪替:發新續期憑證,舊的立刻失效;新續期憑證的 30 天從輪替當下重新起算。
- **FR-013**: 拿已失效的舊續期憑證續期(重放)時,系統 MUST 回 401 `refresh_replayed`,並撤銷該成員全部續期憑證,強制重新登入。
- **FR-014**: 登出 MUST 撤銷當前續期憑證。撤銷只作用在續期憑證;已發出的存取憑證不追蹤狀態,仍可用到 15 分鐘到期。
- **FR-015**: 登入失敗 MUST 以帳號計數:連錯 5 次鎖 5 分鐘;鎖定到期後計數不歸零,再錯 1 次就進下一階
  (10 → 20 → 40 → 60 分鐘,上限 60 分鐘);成功登入計數歸零、階梯退回起點。
  鎖定中一律 401 `unauthorized`,不驗密碼、不透露被鎖、不累計。不存在的 email 不計數,一樣回 401 `unauthorized`。
- **FR-016**: 成員角色 MUST 只有 `member` 與 `staff` 兩種;**沒有任何操作能設定角色**(只能由管理者直接改資料,非目標 11)。
- **FR-017**: 「主辦」MUST 定義為建立該活動的 staff;其他 staff 對別人的活動一律 403 `forbidden`。
- **FR-018**: 活動、票種、保留與確認、訂單各項操作 MUST 依原文授權欄要求身分(成員 / staff / 僅主辦 / 僅本人 / 本人或主辦)。帳號四項原文沒有授權欄。

**活動**

- **FR-020**: 只有 staff MUST 能建立活動(否則 403 `forbidden`);欄位:名稱(1–100 字)、開賣時間、截止時間(開賣 < 截止,可以是過去時間)、
  團體門檻(≥ 2,預設 4)、團體折扣百分比(0–100,預設 10)、保留時長(5–30 分鐘,預設 10)。不合規則 → 400 `invalid_input`。
- **FR-021**: 每個活動的座位 MUST 固定為 10×10 = 100 席 = 活動總容量,編號為列 A–J × 欄 1–10(A1 … J10);
  不做無座位活動;不做真實場館座位圖(非目標 4)。
- **FR-022**: 活動建立後 MUST 直接是開賣中;草稿(`draft`)只由直接改資料進出。
- **FR-023**: 活動狀態 MUST 只有 草稿 → 開賣中 → 已截止 → 已結束;不做活動取消;沒有 已截止 → 開賣中。
  過了截止時間**不**自動轉已截止。已結束目前只能由管理者直接改資料。
  **【待作者確認】**:原文寫「`finished` 由排程或 SQL」,是否要在截止時間之後由排程轉已結束,repo 目前沒有這個排程。
- **FR-024**: 活動列表 MUST 預設包含開賣中、已截止、已結束,不含別人的草稿;主辦看得到自己的草稿;
  可依狀態篩選(草稿 / 開賣中 / 已截止 / 已結束),其他值 → 400 `invalid_input`;篩選只看狀態,「開賣中」不排除已過截止時間的活動。
- **FR-025**: 活動明細 MUST 含票種、剩餘名額、座位狀態。座位狀態分四種:空、他人保留中、已售、自己的(自己保留中的)。
  座位只有在「保留中且到期時間 > 現在」時算保留中。別人的草稿活動 → 404 `not_found`。
  **【待作者確認】**:repo 現況把「自己已確認的座位」也顯示為「自己的」,與答案(只算自己保留中的)不同。
- **FR-026**: 只有主辦 MUST 能改活動(否則 403 `forbidden`)。可改:名稱、開賣時間、截止時間、保留時長、團體門檻、團體折扣,以及各票種名額(一次可改多個)。
  票種名額的修改**全有全無**:任一項小於已售出 → 409 `capacity_below_sold`;名額總和 > 100 → 409 `capacity_exceeded`;兩種情況整次修改都不寫入。
  已售 = 名額 − 剩餘(保留中的座位算已售)。改時間不影響活動狀態。
- **FR-027**: 改保留時長 MUST 只影響之後建立的保留。
- **FR-028**: 只有主辦 MUST 能手動提前截止;截止 MUST 只擋新保留,既有有效保留仍可在到期前確認。
  對非開賣中的活動截止(含重複截止)→ 409 `terminal_state`。

**票種**

- **FR-030**: 只有主辦 MUST 能新增票種(否則 403 `forbidden`),活動在任何狀態都可新增;欄位:名稱、價格(整數分 ≥ 0)、名額(0–100)、
  早鳥截止時間(可省略 = 沒有早鳥)、早鳥折扣百分比(預設 0,0–100);同一活動所有票種名額總和 MUST ≤ 100,超過 → 409 `capacity_exceeded`。
- **FR-031**: 只有主辦 MUST 能改票價;改票種只能改價格。
- **FR-032**: 0 元票種 MUST 允許,折扣不起作用。

**保留**

- **FR-040**: 成員 MUST 能對一個活動保留:一個票種 + 一個或多個座位;**全部成功或全部失敗**。
  座位清單為空、同請求內重複、編號不在 A–J × 1–10 → 400 `invalid_input`;票種不屬於此活動 → 404 `not_found`。
- **FR-041**: 一次保留 MUST 最多 10 席,超過 → 400 `invalid_input`。
- **FR-042**: 一位成員在同一活動 MUST 同時最多一個有效保留;已有時再保留 → 409 `hold_exists`。已買過同一活動仍可再保留。
- **FR-043**: 只有活動狀態為開賣中、且開賣時間 ≤ 現在 < 截止時間時 MUST 能建立保留;兩個條件都要檢查,任一不符 → 409 `not_on_sale`。
- **FR-044**: 保留的到期時間 MUST = 建立時間 + 該活動當下的保留時長。
- **FR-045**: 票種名額 MUST 在建立保留時扣除;放棄、過期、取消訂單三種情況都 MUST 還回。
- **FR-046**: 售出以座位為準(座位唯一是第一道上限),票種名額是第二道上限;座位衝突 → 409 `seat_taken`;名額不足 → 409 `sold_out`;
  兩者同時發生時 MUST 回 `seat_taken`。
- **FR-047**: 保留過期後,座位 MUST 能被別人搶到,不需等待背景清理(釋放與搶到可以在同一次操作中發生);
  系統另外每 5 分鐘清理一次沒人來搶的過期保留。
- **FR-048**: 現在時間 ≥ 到期時間即視為過期;到期那一刻原持有人的確認 MUST 失敗。
- **FR-049**: 保留中 MUST NOT 能改座位或票種。
- **FR-050**: 只有保留本人 MUST 能放棄、確認、試算該保留;別人 → 404 `not_found`。放棄非保留中的保留 → 409 `terminal_state`;
  放棄後保留狀態為已取消。
- **FR-051**: 過期、放棄、取消的保留與訂單紀錄 MUST 留著不刪,只改狀態,留下「誰在什麼時候放掉座位」的證據。

**確認與訂單**

- **FR-060**: 確認 MUST 只檢查保留自己的到期時間,不檢查活動狀態或截止時間;已過期 → 409 `hold_expired`。
- **FR-061**: 確認 MUST 建立訂單(201);可帶優惠碼;以確認當下的票種價格計價(保留不鎖價)。
- **FR-062**: 同一保留已確認時,再確認 MUST 回同一張訂單(200),不建第二張,不看這次帶的優惠碼、也不看到期時間;
  訂單已取消後再確認 → 409 `terminal_state`。
- **FR-063**: 訂單明細 MUST 存價格快照;確認後金額 MUST 不因改價而改變。
- **FR-064**: 訂單狀態 MUST 依原文狀態機:保留中 → 已確認 → 已報到;保留中 → 已過期;保留中 → 已取消;已確認 → 已取消。
  已報到只由 staff 直接改資料標記;已取消是終態,轉任何狀態 → 409 `terminal_state`。
- **FR-065**: 本人 MUST 能取消已確認的訂單,不受活動狀態或時間限制,座位釋放可再售;已報到不可取消(409 `terminal_state`);
  別人的訂單 → 404 `not_found`。

**折扣**

- **FR-080**: 一筆訂單 MUST 只套一種折扣 —— 讓應付金額最低的那一種;都不符合時應付 = 小計。
- **FR-081**: 小計 MUST = 各座位票價加總(一個保留一個票種)。
- **FR-082**: 早鳥:建立保留的時間早於該票種的早鳥截止時間時符合,折扣為該票種的早鳥百分比;沒有早鳥截止時間 = 沒有早鳥。
- **FR-083**: 團體:同一保留的座位數 ≥ 活動的團體門檻時符合,折扣為活動的團體百分比。
- **FR-084**: 優惠碼:確認時輸入,是現金券(折固定金額);同一碼可多人用,每人每活動一次(只算有效訂單,已取消訂單用過的碼可再用);
  可限定某活動或全站適用;「現在 < 有效期限」才有效(確認時用確認時間);碼不分大小寫。
  無效 = 不存在、過期、不屬於此活動、已用過。
- **FR-085**: 無效優惠碼:
  - 存在但無效的碼,假設有效時會讓應付**嚴格**低於其他最佳折扣 → 409 `promo_rejected`;同額或較差 → 忽略碼,訂單照擇優成立。
  - 不存在的碼:有別的折扣 → 忽略;沒有別的折扣 → 409 `promo_rejected`。
  - 沒有任何別的折扣時,無效碼一律 409 `promo_rejected`(含小計為 0)。
    **【待作者確認】**:repo 現況對「存在但無效」的碼在小計為 0 時是忽略(201),不是 409。
- **FR-086**: 平手時 MUST 依序選 優惠碼 → 早鳥 → 團體;平手順序只用在有效折扣之間。
- **FR-087**: 優惠碼大於小計時只折到 0;訂單記的折抵金額 = min(碼面額, 小計)。
- **FR-088**: 訂單 MUST 只記被套用的那一種:早鳥百分比、團體百分比、優惠碼折抵三者只有一個非 0;
  優惠碼沒被選中時(含小計為 0,「不划算」)不記碼、折抵為 0、碼不算用掉。
- **FR-089**: 百分比折扣 MUST 以整數百分比表示,結果四捨五入到最小金額單位,計算全程只用整數(原文公式:應付 = ⌊(小計 × (100 − 折扣%) + 50) / 100⌋)。

**試算**

- **FR-066**: 本人 MUST 能對自己保留中的保留試算(可帶優惠碼):回原價、套用哪種折扣、應付金額、碼狀態;不建訂單、不用掉碼。
  碼狀態為 無碼 / 已套用 / 不划算 / 無效 四種之一;碼的有效期以試算當下時間判斷。
  已過期 → 409 `hold_expired`;已放棄或已確認 → 409 `terminal_state`;別人 → 404 `not_found`。

**我的票券與明細**

- **FR-070**: 訂單明細 MUST 只給本人或該活動主辦看,其他人 → 404 `not_found`;含金額快照與票券 QR。
- **FR-071**: 成員 MUST 能看「我的票券」列表:本人所有訂單(含已取消與已報到),不含保留,依確認時間新到舊。
- **FR-072**: 票券 QR MUST 是訂單 id + 簽章的短字串,不含任何個資;已取消的訂單明細仍含 QR 內容;不做查驗與核銷端(非目標 13)。

**客戶端**

- **FR-073**: web MUST 只有五個畫面:登入/註冊、活動列表、活動頁(10×10 選位)、保留倒數與確認、我的票券(含 QR);沒有第六個。
  主辦操作只透過 API,五個畫面不放主辦功能(非目標 11)。保留倒數畫面有「放棄」;我的票券只對已確認訂單顯示「取消訂單」。
- **FR-074**: web MUST 把 API 回的錯誤代碼翻成繁體中文顯示;API 本身只回代碼。
- **FR-075**: web 的保留確認畫面 MUST 有「套用」優惠碼按鈕,呼叫試算。
- **FR-076**: iOS MUST 只有:登入、活動列表 → 活動明細(唯讀座位圖)、我的票券列表與明細;不做選位;只做票券的離線讀取快取;
  寫入一律需要連線(非目標 8)。
- **FR-077**: web 與 iOS 對同一筆票券資料 MUST 顯示同一份資料。
- **FR-078**: 只做繁體中文(非目標 10);UI 用系統元件,不追求精緻度與完整無障礙,放大字級不崩壞即可(非目標 15)。
  金額顯示為 NT$ 加千分位,整元不顯示小數,有分才顯示兩位(12345 分 → NT$123.45;100000 分 → NT$1,000),轉換全程整數;
  web 時間以瀏覽器時區、繁中格式顯示。

**金額與錯誤**

- **FR-079**: 所有金額 MUST 以整數最小單位(分)計算與儲存,計算路徑不得出現浮點;轉成「元」只在顯示層做。
- **FR-090**: 錯誤回應 MUST 是錯誤代碼,完整清單與狀態碼:

  | 代碼 | 狀態 | 何時 |
  |---|---|---|
  | `invalid_input` | 400 | 欄位不合規則、保留超過 10 席或座位清單不合法、保留時長越界、列表篩選值不合法 |
  | `unauthorized` | 401 | 未登入、帳密錯誤、帳號鎖定中、不存在的 email |
  | `refresh_replayed` | 401 | 重放已失效的續期憑證 |
  | `forbidden` | 403 | 非 staff 建活動;非主辦改活動、截止、新增票種、改票價 |
  | `not_found` | 404 | 資源不存在;別人的保留或訂單;別人的草稿活動;票種不屬於此活動 |
  | `email_taken` | 409 | 重複 email |
  | `not_on_sale` | 409 | 活動不是開賣中,或時間不在開賣區間 |
  | `seat_taken` | 409 | 座位已被占(與名額不足同時發生時也回這個) |
  | `hold_exists` | 409 | 同活動已有有效保留 |
  | `sold_out` | 409 | 票種名額不足 |
  | `hold_expired` | 409 | 確認或試算已過期的保留 |
  | `terminal_state` | 409 | 放棄非保留中的保留;試算已放棄或已確認的保留;訂單已取消後再確認;取消已報到或已取消的訂單;截止非開賣中的活動 |
  | `capacity_below_sold` | 409 | 名額改到小於已售 |
  | `capacity_exceeded` | 409 | 票種名額總和 > 100 |
  | `promo_rejected` | 409 | 見 FR-085 |

- **FR-091**: 「僅本人」的資源(保留、訂單)對別人一律 404 `not_found`,不透露存在;主辦限定的寫入(活動、票種)對非主辦 403 `forbidden`;
  別人的草稿活動 → 404 `not_found`。訂單明細例外:該活動主辦也可以看(FR-070)。

### Key Entities *(include if feature involves data)*

- **成員**:email(唯一,小寫保存)、密碼、暱稱、角色(`member` / `staff`)、登入失敗狀態(連續失敗次數、鎖定到期時間;作者已決定記在成員資料上)。
- **續期憑證**:屬於一位成員;有到期時間與撤銷時間;只存雜湊不存原值;可單筆撤銷(登出)或整位成員批次撤銷(重放)。
- **活動**:名稱、開賣時間、截止時間、團體門檻、團體折扣百分比、保留時長、狀態、主辦(建立者)。固定 100 席(A1 … J10)。
- **票種**:屬於一個活動;名稱、價格(最小單位)、名額、剩餘名額、早鳥截止時間(可空)、早鳥折扣百分比。同一活動名額總和 ≤ 100。
- **座位保留**:活動 + 座位編號 + 狀態;同一活動同一座位在「保留中或已確認」時最多一筆;過期、放棄、取消的列留著不刪。
- **保留 / 訂單**:屬於一位成員與一個活動、一個票種、1–10 個座位;有到期時間;狀態依 FR-064。
  確認後帶金額快照:各座票價、小計、被套用的那一種折扣(早鳥百分比 / 團體百分比 / 優惠碼與實際折抵,只有一個非 0)、應付金額、確認時間。
- **優惠碼**:碼(不分大小寫)、折扣金額(現金券)、有效期限、適用活動(可為空 = 全站)。每人每活動的使用紀錄以「訂單上存的優惠碼」表示,不另開紀錄。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對同一票種併發送出 N 次保留,成功數 ≤ 名額,且「已售 + 剩餘 = 名額」對得起來。
- **SC-002**: 併發搶同一座位,恰好一個成功。
- **SC-003**: 到期那一刻(現在 = 到期時間)的三方競態有自動化測試釘住:原持有人的確認一律失敗。
- **SC-004**: 金額計算路徑中出現浮點數的次數為 0,並有自動檢查可證明;US4 情境 1 的例子算出 90000 分。
- **SC-005**: 原文「必須被測試證明的規則」十條,每條都有對應的自動化測試且通過;開賣與截止兩個時間邊界(含相等那一刻)的測試分開寫。
- **SC-006**: 非主辦(一般成員或其他 staff)改活動、提前截止、改票價,100% 回 403,有測試證明。
- **SC-007**: 確認後改票價,重讀訂單金額 100% 不變。
- **SC-008**: 同一成員同一筆票券,web 與 iOS 顯示的資料一致(金額、座位、狀態、QR)。
- **SC-009**: 「我的票券」一次載入的資料讀取列數有被量測並記錄下數字;沒有目標值。
- **SC-010**: 登入憑證的邊界行為由原文指定的六個測試與常數時間簽章比對檢查裁定,全部通過。
- **SC-011**: 對外操作數量 = 18,web 畫面數量 = 5,沒有超出。
